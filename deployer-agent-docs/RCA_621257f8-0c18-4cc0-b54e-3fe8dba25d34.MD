# RCA — Fork·Fate "Where your visitors are" all Kansas City (production)

## TL;DR
The stale-deploy theory is **REFUTED**. The current production backend **already contains the geo fix** (`_CDN_HOP_CIDRS` + `_purge_lb_ip_records`). Despite that, production is **still** geolocating every visitor to Kansas City, including pageviews written days *after* the deploy. So the deployed fix is present but **ineffective in production** — almost certainly because the CDN/LB-hop stripping was calibrated to the **preview** load balancer and does not match production's actual proxy chain.

## What was verified (evidence)

### Q1 — Last prod deploy & does the running backend contain `_CDN_HOP_CIDRS`?
- **Last successful production deploy:** run `621257f8-0c18-4cc0-b54e-3fe8dba25d34`, type=redeploy, trigger=user_deploy, completed **2026-09-20T17:28:24Z**. This is the current `active_run_id`.
- **The deployed image's pulled source DOES contain the fix.** Grep of the run's pull_source (extracted in an eph sandbox for run `621257f8`):
  - `backend/core.py:352: _CDN_HOP_CIDRS = [ipaddress.ip_network(_c) for _c in (`
  - `backend/core.py:367: return any(ip in net for net in _CDN_HOP_CIDRS)`
  - `backend/core.py:609: def client_ip(request: Request) -> str:`
  - `backend/routes/stats.py:149: async def _purge_lb_ip_records(request: Request):` (called at stats.py:212)
- **Conclusion:** the production deploy does **NOT** predate the geo fix. The `_CDN_HOP_CIDRS` change and the one-time purge routine are both compiled into the live image. The frontend `FF_BUILD "2026.06-626"` tag is a red herring — the frontend build label does not track backend commits, and the backend clearly carries the fix.
- **Not verified:** I was unable to read the exact *contents* of the `_CDN_HOP_CIDRS` list — the eph sandbox exec repeatedly timed out (`eph 504 exec_timeout`) after the initial grep. This matters (see hypothesis below), so it should be confirmed by reading the committed source directly.

### Q2 — Production MongoDB (`geo_cache`, `pageviews`)
DB: `web-fate-launch-fork_fate`.
- **`geo_cache`:** 2 documents. **Both `city: "Kansas City", region: "Missouri"`** — but under **two DISTINCT `ip_hash`** values (`02cd9993…`, `bd4fe143…`), not a single shared hash. (Collection is small because entries carry a TTL `expire_at`.)
- **`pageviews`:** 149 documents. **`distinct(city)` = ["Kansas City"] only** — 100% of pageviews are Kansas City.
- **`distinct(ip_hash)` on pageviews = 8 values**, all resolving to Kansas City. Most common is `bd4fe14366153cb83803d499a0a5b3dc` = 14 of 149.
- **Recency (the decisive point):** the newest pageviews are `ts` **2026-09-30T14:31:55Z**, **2026-09-30T01:11Z**, **2026-09-29T18:40Z**, etc. — i.e. records are **STILL being written as Kansas City well AFTER the 2026-09-20 deploy** that contains the fix.
- **Nuance vs. the original theory:** it is NOT "one single ip_hash." There are 8 distinct hashes — so different requests ARE producing different hashed IPs — yet every one geolocates to Kansas City / Missouri. That is the classic GeoIP behavior for **non-client / unlocatable US IPs collapsing to the US-center (Kansas/Missouri) fallback**, which points at the app still hashing/geolocating an infrastructure hop rather than the true client — the exact failure mode the fix was meant to eliminate.

### Q3 — Production X-Forwarded-For shape
- **Cannot be answered from logs.** The app does not log the raw `X-Forwarded-For` (or CF headers). `fetch_app_logs` over the last 24h with an XFF/forwarded/client_ip/`35.186` filter returned **0 lines**. Production's header chain shape is therefore **unverified** — there is no current signal to compare against preview's `<client>,<cloudflare-edge>,<lb-ip>` chain.

## Root cause (assessment)
The fix is deployed but does not correct production geolocation. Given (a) the fix code is present, (b) records written after the deploy are still 100% Kansas City, and (c) 8 distinct hashes all collapse to the US-center GeoIP fallback, the most probable cause is:

> `_CDN_HOP_CIDRS` / the rightmost-XFF-hop stripping was calibrated to the **preview** load balancer egress (the preview LB IP `35.186.245.91` referenced in the ticket). **Production sits behind a different Google Cloud LB / Cloudflare egress range**, so in prod the code either (i) does not recognize the prod LB hop as a CDN hop and keeps hashing an infra IP, or (ii) strips one hop but still lands on a Google/CF internal IP — both of which GeoIP to Kansas City. Because those infra IPs vary slightly per request, you get several distinct `ip_hash`es all resolving to the same KC fallback.

Additionally, `_purge_lb_ip_records` evidently did **not** clear the bogus records (the KC entries persist and new ones keep arriving), so even after the real fix lands the historical/ongoing KC rows need purging.

**Confidence:** Q1 and Q2 are verified from the deployed source and live prod DB. The root-cause mechanism is **inferred, not reproduced** — I could not read the exact CIDR list (eph timeouts) and prod XFF is not logged, so the precise prod chain is unconfirmed.

## Recommended fixes (owner: Code / E1)
1. **Make CDN/LB-hop detection production-aware.** Do not rely on a preview-specific CIDR. Either: trust a fixed proxy-hop count for the prod topology, include the published Google Cloud LB + Cloudflare IP ranges in `_CDN_HOP_CIDRS`, or resolve the true client from a header known-good in prod. Validate against a real production XFF sample.
2. **Temporarily log the raw `X-Forwarded-For` (and any `CF-*` headers) in production** so the actual chain shape can be captured — it is currently unlogged, which is why prod's header shape is unverifiable. This will confirm whether prod adds extra hops vs. preview.
3. **Re-run / repair the purge** (`_purge_lb_ip_records`) so existing Kansas City records under infra-derived `ip_hash`es are removed once the corrected client-IP logic is live.

No deployment was performed as part of this investigation, per instructions.
